# 確定申告支援ツール(kakuteishinnkoku)

日本の個人向け確定申告を支援するセルフホスト型Webアプリ。
暗号資産・株式等投資の損益計算と、マネーフォワード MEからのデータ取り込みに対応する。

このリポジトリは「ルーティンごとにブラッシュアップする」開発方針で育てている。
1回のセッションで全部を作り切るのではなく、都度機能を積み増していく。
現在の到達点と次にやるべきことは、このREADME末尾の「ロードマップ」を参照。

## 技術スタック

- Next.js 16 (App Router, Server Actions) + TypeScript
- Tailwind CSS v4
- Prisma 6 + SQLite(ローカルファイルDB。個人利用前提でクラウドDBは使わない)
- decimal.js(金額計算を浮動小数点誤差なく行うため、円建て金額は全てDecimalで扱う)
- jose(パスワード認証のセッションCookie(JWT)の署名・検証)
- Vitest(計算ロジックのユニットテスト)

## セットアップ

```bash
npm install
cp .env.example .env   # DATABASE_URL="file:./dev.db"
npx prisma db push     # ローカルSQLiteにスキーマを反映
npm run dev            # http://localhost:3000
```

自宅サーバー等インターネットからアクセス可能な場所にホスティングする場合は、
`.env`に`AUTH_PASSWORD`と`SESSION_SECRET`を設定するとパスワード認証を有効化できる
(機能15参照)。ローカルのみで使う場合は未設定のままでよい(認証なしで動作する)。

テストと型チェック:

```bash
npm run test
npx tsc --noEmit
npm run lint
```

## 機能(現時点)

### 0. 前年繰越残高(期首残高) — `src/lib/openingBalance.ts`

複数年にまたがって暗号資産・株式等を保有している場合、総平均法・移動平均法の
計算にはその年の期首時点の保有数量と取得価額合計が必要になる。`/import`
ページの「期首残高(前年からの繰越)」セクションから、銘柄ごとに期首残高を
手入力できるほか、「前年の期末残高から自動で繰り越す」ボタンで前年分の
計算結果(期末残高)をそのまま当年の期首残高として一括登録できる
(既に登録済みの銘柄は上書きしない)。NISA口座分は課税口座と別ロットとして
別途登録する。

### 1. 暗号資産(仮想通貨)の損益計算 — `src/lib/crypto/`

国税庁の「暗号資産に関する税務上の取扱いについて(FAQ)」に基づき雑所得を計算する。
購入・売却・暗号資産同士の交換(TRADE_IN/TRADE_OUT)・マイニング等の受取
(INCOME)・暗号資産建て手数料(FEE)に対応。

暗号資産取引所(bitFlyer・Coincheck・GMOコイン等)の「取引履歴」CSVも
`src/lib/crypto/exchangeCsv.ts` から取り込める。よく使われる列見出しは
エイリアスで自動判定しつつ、一致しないCSVは `/import` 画面でヘッダー名を
ユーザー自身が指定する汎用マッピング方式でも取り込める。これにより、未検証の
取引所固有フォーマットを誤って解釈するリスクを避けながら、仕様変更や表記ゆれの
あるCSVにも対応する。現状は円建ての現物売買(買い/売り)のみに対応しており、
暗号資産同士の交換やマイニング等の受取はCSVからは取り込めない(手入力で対応する)。

評価方法は**総平均法**(届出が無い場合の法定算出方法。その年の期首残高と
年間取得分を合算した加重平均単価を、その年の全ての譲渡に適用する)と
**移動平均法**(税務署への届出により選択可能。取得の都度平均単価を更新し、
譲渡時点の平均単価を取得費とする)のいずれかを、課税年度ごとにダッシュボードから
選択できる(`TaxYear.cryptoCostMethod`)。移動平均法を選ぶ場合は各取引の取引日時
(tradedAt)が計算に必須になる。

暗号資産取引所(bitFlyer・Coincheck・GMOコイン等)の「取引履歴」CSVも
`src/lib/crypto/exchangeCsv.ts` から取り込める。取引所ごとに専用パーサーを
用意するのではなく、日時・銘柄ペア・売買種別・数量・単価(または合計金額)・
手数料という共通項目に対して、よく使われる列見出し表記をエイリアスとして
幅広く登録する汎用パーサーとして実装している。現状は円建ての現物売買
(買い/売り)のみに対応しており、暗号資産同士の交換やマイニング等の受取は
CSVからは取り込めない(手入力で対応する)。

### 2. 株式・投資信託等の譲渡損益計算 — `src/lib/investment/`

所得税法施行令118条に基づく「総平均法に準ずる方法」(実務上の移動平均法)で
取得費を計算し、譲渡所得(申告分離課税)を算出する。NISA口座は課税口座と
別ロットとして扱い、非課税の参考値として分離表示する。配当等は損益計算とは
別に集計する。上場株式等と一般株式等(非上場株式)は別プールの申告分離課税
として扱い(`InvestmentTrade.isListed`。機能54参照)、損益通算はできない。
一般株式等の譲渡損失には繰越控除制度(措置法37の12の2)が無いため、赤字の
場合は当年限りで切り捨てる。

### 3. マネーフォワード ME 連携 — `src/lib/moneyforward/`

マネーフォワード MEの「家計簿」CSVエクスポートを取り込める。ヘッダー名で
カラムを特定するため列順の変更に強く、1行の解析に失敗しても
(不正な日付・金額など)その行だけスキップして処理を継続する。

### 4. 暗号資産取引所CSVの取り込み — `src/lib/crypto/exchangeCsv.ts`
bitFlyer(現物取引履歴CSV)・Coincheck(業界標準フォーマットCSV)・GMOコイン
(取引履歴CSV)・bitbank(約定履歴CSV)のエクスポートファイルを取り込める。
いずれも現物取引の行のみが対象で、信用・証拠金取引やレバレッジ取引の行は
自動では取り込まずスキップする(建玉の決済損益で課税所得が決まるため、
本ツールの現物取引モデルにはそのまま当てはめられない)。各取引所のCSV仕様は
非公式(取引所側の仕様変更で崩れる可能性がある)なため、マネーフォワードの
パーサーと同様「解釈できない行はスキップして処理を継続し、件数を報告する」
方針を取る。特に入出金(送付・受取)・証拠金取引・税務上の性質が一意に
決まらない明細(増加/減少の一方のみの行など)は誤って課税イベントとして
取り込むより安全側に倒してスキップし、必要であれば手動登録を促す。
取り込んだ内容は必ず `/import` の一覧で確認すること。また、列見出しが
プリセットと一致しないCSVや未検証の取引所CSVは、`/import` 画面で
「その他 / 手動マッピング」を選ぶと、まず日付・銘柄・売買種別・数量・
単価(または合計金額)・手数料によく使われる列見出し(日本語・英語、
`src/lib/crypto/exchangeCsv.ts`の`HEADER_ALIASES`参照)からの**自動認識**
(`parseCryptoExchangeCsv`)を試みる。自動認識できなかった場合のみ、
日付/銘柄/売買種別/数量/単価/手数料の列名を指定する**汎用マッピング方式**
(`parseMappedExchangeCsv`)にフォールバックする。マッピング欄を入力した
場合は自動認識より優先される。

bitbankの「約定履歴」CSVも同様に取り込める。「現物/信用」列が"現物"の行のみを
対象にし、信用取引の行は対象外としてスキップする。

### 5. 前年繰越残高(期首残高)の管理 — `src/lib/openingBalance.ts`

暗号資産・株式等とも、複数年にまたがって保有している場合の期首残高を
`/import` 画面から登録できる。銘柄ごとに手入力するほか、「{前年}年分の
期末残高から繰り越す」ボタンで前年分の取引から期末残高を自動計算し、
当年分の期首残高として一括登録できる(既存の登録は上書きされない)。
株式等はNISA口座・課税口座を別ロットとして繰り越す。

### 6. 配当所得の課税方式シミュレーション — `src/lib/investment/dividendTaxSimulation.ts`

上場株式等の配当所得について、総合課税・申告分離課税・申告不要のどの方式を
選ぶと税負担が最も軽くなるかを試算する(ダッシュボードの「配当所得の課税方式を
シミュレーションする」から利用)。配当以外の課税所得金額や、損益通算できる
上場株式等の譲渡損失額を入力すると、方式ごとの国税・住民税の試算額と、
配当控除額・損益通算に使った損失額を比較表示する。所得税は速算表による
超過累進税率、住民税は10%固定(均等割は含まない)で計算する概算値である。
配当控除率は銘柄種別(`InvestmentTrade.assetType`)により通常税率
(上場株式等・ETF)・半分税率(株式投資信託等、外貨建資産等の組入割合50%以下)・
1/4税率(株式投資信託等、組入割合50%超。`InvestmentTrade.mutualFundHighForeignRatio`
で判定。機能57参照)・対象外(公社債投資信託・J-REIT等)の4区分に自動判定し、
`/import`で登録済みの取引から集計した内訳を初期値として表示する(機能45参照)。
### 7. 上場株式等の譲渡損失の繰越控除(3年間) — `src/lib/investment/lossCarryforward.ts`

確定申告により繰越控除の適用を受けた上場株式等の譲渡損失は、発生した年の
翌年以後3年間、上場株式等の譲渡所得等の金額から控除できる(暗号資産の損失は
雑所得のため損益通算・繰越の対象外)。`/import`ページの「上場株式等の譲渡損失の
繰越控除(3年間)」セクションから、発生年ごとに年初時点で残っている繰越損失残高を
手入力できるほか、「前年分の計算結果から自動で繰り越す」ボタンで前年分の
繰越控除計算結果(未使用の繰越残高)をそのまま当年分に一括登録できる
(既に登録済みの発生年は上書きしない)。控除は発生年の古いものから優先して
適用し、発生年から3年を超えた残高は自動的に控除対象から除外(期限切れとして
表示)する。ダッシュボードの「譲渡所得(株式等)」は繰越控除適用後の課税対象額を
表示し、下書きCSV(`src/lib/etax/csvExport.ts`)にも繰越控除の使用額・翌年繰越額・
期限切れ額を出力する。

### 8. 暗号資産の証拠金(レバレッジ)取引の決済損益 — `src/lib/crypto/marginCalculator.ts` / `src/lib/crypto/marginCsv.ts`

DMM Bitcoin・SBI VCトレード等の証拠金(レバレッジ)取引は、現物取引のように
数量×単価で取得費を積み上げる総平均法/移動平均法の計算モデルにはあてはまらず、
決済(反対売買)のたびに確定する**建玉損益**がそのまま雑所得の収入・損失になる。
そのため`CryptoTrade`(現物)とは別に`CryptoMarginTrade`テーブルを設け、決済ごとの
損益(手数料控除・スワップポイント加算後)を単純に合算するだけのシンプルな
計算エンジンとした(期首残高・取得原価の概念を持たない)。`/import`ページの
「暗号資産の証拠金(レバレッジ)取引の決済損益」セクションから手入力できるほか、
取引所ごとのCSV仕様の差異が大きく未検証のため専用プリセットは用意せず、
決済日時・銘柄・決済損益・手数料・スワップの列名を指定する汎用マッピング方式で
CSV取り込みにも対応する。ダッシュボードの「雑所得(暗号資産)」・下書きCSVの
出力額は、現物取引分と証拠金取引分の合計値を表示する。

### 9. 証券会社の特定口座年間取引報告書との突合 — `src/lib/investment/annualReportReconciliation.ts`

証券会社が発行する「特定口座年間取引報告書」の「譲渡の対価の額(収入金額)」
「配当等の額」を、証券会社・口座区分ごとに`/import`画面から入力する
(`src/lib/investment/annualReportCsv.ts`によるCSV一括取り込みにも対応。
証券会社・口座区分ごとの年間サマリー数値を1行にまとめたCSVを想定し、
年間取引報告書自体はPDF発行が主流で様式も証券会社ごとに異なり未検証のため、
他の取引所CSVと同様に列名を指定する汎用マッピング方式のみを提供する。
口座区分は「特定口座(源泉徴収あり/なし)」「一般口座」等の表記ゆれを
ある程度吸収し、判定できない行は安全側に倒してスキップする)と、
アプリに登録済みの同じ証券会社・口座区分の売却・配当の取引明細から計算した
金額と自動で突き合わせ、差額があれば「不一致」として一覧に表示する
(1円未満の端数差は許容する)。収入金額・配当等の額はその年の実績値の
単純合計として計算できるため、前年繰越や取得費の平均単価計算に依存せずに
検証でき、証券会社の記録と照合することで取引の入力漏れ・入力ミスを検知
できる。「取得費及び譲渡に要した費用の額等」は証券会社が口座ごとに個別
管理する取得原価であり、本ツールの譲渡所得計算(`src/lib/investment/calculator.ts`)
は銘柄単位・全口座合算で平均単価を計算するため前提が異なる(同一銘柄を
複数の証券会社・口座で保有している場合、口座ごとの取得費は一致しない)。
そのため取得費・差引金額は自動突合の対象にはせず、参考表示のみ行う。

### 10. 確定申告書作成コーナー向け下書きCSV出力 — `src/lib/etax/`

暗号資産・投資の年間集計を、申告書の該当欄と対応付けたCSVとして
ダウンロードできる(ダッシュボードの「下書きCSVをダウンロード」ボタン)。

**重要な制約:** 個人が保有するマイナンバーカードでe-Taxへ電子署名・送信する
処理は、国税庁の「確定申告書等作成コーナー」または「e-Taxソフト」経由でしか
行えない。第三者ツールが認証情報を代行してe-Taxへ直接送信する公式なAPIは
存在しないため、本ツールはe-Taxへの自動送信は行わない。出力されるCSVは
あくまで「確定申告書等作成コーナー」に転記する際の下書き・集計資料であり、
国税庁公式のインポート形式ではない。

暗号資産・投資の所得区分に加えて、医療費控除・生命保険料控除・社会保険料
控除等の各試算画面で年分ごとに登録済みの所得控除(`IncomeDeduction`)がある
場合は「■ 所得控除サマリー」欄も出力され、区分ごとの所得税・住民税の控除額と
申告書での主な記載箇所(第一表のどの欄か等)を一覧できる。医療費控除と
セルフメディケーション税制のように選択制で併用できない組み合わせは、
合計額に有利な方のみを計上している旨を注記として出力する。基礎控除等、
本ツールで試算していない所得控除は引き続き各自で申告書に転記する必要がある。

`/mortgage-deduction`で登録済みの住宅ローン控除額(税額控除)がある場合は
「■ 税額控除(住宅ローン控除)」欄も出力される(機能47参照)。外国税額控除は
当年分の試算結果がDBに保存されないため引き続きCSVには含まれず、
`/foreign-tax-credit`の試算結果を別途申告書へ転記する必要がある
(ロードマップ参照)。

### 11. マネーフォワード資産残高との突合(取引漏れ検出) — `src/lib/moneyforward/`

マネーフォワード ME の「資産の内訳」画面からダウンロードしたCSV(資産残高
スナップショット)を取り込み、残高がある金融機関(取引所・証券会社)の
うち、アプリに同じ名前の暗号資産・投資取引明細が1件も登録されていない
ものを「計上漏れの疑い」として`/import`画面に一覧表示する。逆に、アプリ
には取引明細があるのにマネーフォワード側の資産残高に見当たらない金融機関も
参考情報として表示する(資産の移管やマネーフォワード未連携の口座でも
起こりうるため、こちらは計上漏れとは限らない)。

証券会社の年間取引報告書との突合(機能9)と同様、この突合は自動判定できる
範囲(ここでは金融機関名の一致)に限定している。金融機関名はアプリ側の
取引所名・証券会社名の入力と完全一致(前後の空白のみ正規化)で突き合わせる
ため、表記を揃えて登録する必要がある。CSVの列見出しは公開情報から確認
できておらず未検証のため、専用プリセットは用意せず、暗号資産取引所CSVの
手動マッピング方式と同様に列名を指定する汎用マッピングのみで取り込む。

`AssetSymbolMapping`にマネーフォワード側の資産名(例:「ビットコイン」)と
アプリ側の銘柄シンボル(例:「BTC」。`/import`の「銘柄マッピング」欄から
年に依存しないマスタデータとして登録する)の対応を登録すると、金融機関
単位よりもう一段細かい「金融機関×銘柄」単位の突合(`reconcileAssetSymbolBalances`)
も行える。評価額は時価に左右され取得原価ベースの保有数量と単純比較できない
ため、既定では「その金融機関にその銘柄の取引明細が1件でもあるか」という
存在判定に留まる。マッピング未登録の資産名は「未マッピング」として判定不能
のまま表示され、計上漏れの判定対象にはならない。

資産残高CSVの取り込みフォームで数量列名を指定すると、評価額と異なり時価に
左右されない「保有数量」そのものの突合も追加で行える(`quantityCheck`)。
アプリ側の期待数量は「その銘柄の期首残高(`OpeningBalance`)+当年の取引に
よる数量の増減」として計算し(暗号資産は`cryptoTradeQuantityDelta`、株式等は
`investmentTradeQuantityDelta`で取引種別ごとの増減方向を判定)、マネーフォワード
側の数量と比較して一致すれば「数量一致」、一致しなければ「数量不一致」
(入力漏れ・入力ミスの可能性)として`/import`画面の「銘柄単位の突合」表に
表示する。期首残高(`OpeningBalance`)は銘柄単位の合計しか管理していない
ため、同一銘柄を複数の金融機関にまたがって保有している場合は、その銘柄の
期首残高をどちらに帰属させるべきか本来判定できない。`/import`の「期首残高の
金融機関別内訳」から`OpeningBalanceByInstitution`にその金融機関の期首数量を
個別登録すれば、その金融機関については按分不要で数量突合できる(未登録の
金融機関は引き続き「判定不能(期首残高の按分不可)」として見送る。1つの
金融機関でのみ保有している銘柄、または期首残高が無い銘柄はそもそも按分の
問題が無いため登録なしで判定できる)。数量列を指定しない場合は従来どおり
存在判定のみになる。

### 12. 外国税額控除の試算 — `src/lib/investment/foreignTaxCredit.ts`

米国株式等、国外で発行された株式・投資信託の配当等は、日本での課税(申告分離
課税20.315%等)に加えて現地国でも源泉徴収されることが多い(米国株の場合、
租税条約により10%が一般的)。この二重課税を調整する外国税額控除(所得税法95条)
について、`/foreign-tax-credit`から控除限度額(所得税・復興特別所得税・
住民税の3つ)と、その年に外国税額控除として使える金額を試算できる。

控除限度額は「所得税額 ×(調整国外所得金額 ÷ 所得総額)」を基準に、復興
特別所得税分(所得税限度額×2.1%)・住民税分(所得税限度額×30%、道府県民税
12%+市町村民税18%の標準割合)を積み上げて計算する。当年の外国所得税額は
まずこの合計限度額から控除し、控除しきれない場合は「控除限度超過額」として
翌年以後3年間繰り越せる。逆に限度額が余った場合はその余り(「控除余裕額」)も
翌年以後3年間繰り越せ、外国所得税額が限度額を超えた将来の年でその超過額に
充当できる(控除限度超過額側の繰越と対になる仕組み。両方向とも対応済み)。
「所得税額」「所得総額」は給与所得等を含む確定申告書全体の金額が必要で、
本ツールは暗号資産・投資以外の所得を管理していないため自動計算せず、
手入力方式のシミュレーターとした(配当所得の課税方式シミュレーションと
同様の位置付け)。一方「国外所得金額」は、`/import`の株式等取引フォームで
配当・分配金または売却に「国外で発行された株式・投資信託等」のチェックを
付けておけば、その年の課税口座分(NISA口座は国内非課税のため対象外)の
配当等と譲渡益(売却時の為替差損益を含む)を合算して`src/lib/investment/
calculator.ts`が自動集計し、`/foreign-tax-credit`を開いた時点の初期値に
反映する(取引明細から追える範囲の自動化で、値そのものは引き続き手入力で
上書き可能)。「外国所得税額」は現地源泉徴収が発生する配当等のみ入力欄が
あり、同様に自動集計・初期値反映される(株式等の譲渡益に対する現地源泉
徴収は通常発生しないため対象外)。取引登録していない国外所得(配当以外の
国外源泉所得等)は引き続き手入力が必要。

繰越控除限度超過額は`ForeignTaxCreditCarryforward`テーブル、繰越控除余裕額は
`ForeignTaxCreditSpareLimitCarryforward`テーブルに、それぞれ発生年(originYear)
ごとに永続化する。`src/lib/investment/foreignTaxCredit.ts`側では、当年の限度額に
余りがあればまず繰越控除限度超過額へ発生年の古い順に充当し(なお余った分は当年
新規発生の控除余裕額として繰り越す)、逆に当年の外国所得税額が限度額を超えた
場合は繰越控除余裕額を発生年の古い順に充当する(それでも控除しきれない分は
当年新規発生の控除限度超過額として繰り越す)。いずれも期限(発生年+3年)を
超えた分は自動的に控除対象から除外する(上場株式等の譲渡損失の繰越控除と同じ
方式)。`/import`ページの「外国税額控除の繰越控除限度超過額」
「外国税額控除の繰越控除余裕額」の各セクションから発生年ごとに手入力できるほか、
`/foreign-tax-credit`の試算結果に翌年以後へ繰り越す額が発生した場合は、その
ページの「◯年分として登録する」ボタンから翌年分として一括登録できる(既に
翌年分に同じ発生年の登録がある場合は上書きしない)。損失の繰越控除の「前年分の
計算結果から自動で繰り越す」ボタンとは異なり、外国税額控除の計算に必要な
所得税額・所得総額等はDBに保存されない都度入力のため、前年分の計算結果を
サーバー側で再計算することはできない。そのため試算画面から直接、当年の計算結果を
翌年分として登録する方式にしている。

### 13. NISA年間投資枠の使用状況試算 — `src/lib/investment/nisaQuota.ts`

2024年以降の新NISA制度は、年間投資枠が「つみたて投資枠(年120万円)」と
「成長投資枠(年240万円)」に分かれており、それぞれ独立して上限を管理する。
`/import`の株式・投資信託等の取引フォームでNISA口座の買付(type=BUY)を
登録する際に、どちらの枠を使った買付かを選択できるようにし
(`InvestmentTrade.nisaType`)、ダッシュボードにその年の枠ごとの使用額・
残枠を表示する(上限を超えている場合は警告表示)。

**制約:** 買付金額は約定代金(数量×単価)を用い、手数料は含めない。また、
NISA口座の買付のうち枠区分が未入力の取引は集計に含めず、金額を「未分類」
として警告表示する。生涯非課税限度額(総枠1,800万円)は機能27で別途試算する。

### 14. 先物取引・FXに係る雑所得等の分離計算 — `src/lib/investment/futuresIncome.ts`

FX(店頭外国為替証拠金取引)・先物・CFD等の決済損益は、所得税法上
「先物取引に係る雑所得等」として、上場株式等の譲渡所得や暗号資産の雑所得とは
別区分の申告分離課税(一律20.315%)の対象になる。上場株式等の譲渡損失とは
損益通算できず、繰越控除(3年間)も別プールで管理しなければならない。

以前は`InvestmentTrade.assetType`に「FX」という選択肢があったが、内部的には
株式等と同じ数量×単価の移動平均法(譲渡所得)としてしか計算されておらず、
上場株式等の譲渡損益・NISA枠・繰越控除の集計にそのまま混入してしまう不具合
だった。今回、`InvestmentTrade`とは独立した`FuturesTrade`テーブル・
`src/lib/investment/futuresIncome.ts`を新設し、暗号資産の証拠金取引
(`CryptoMarginTrade`)と同様に「建玉の決済(反対売買・差金決済)のたびに
確定する損益をそのまま合算する」モデルで計算するようにした。繰越控除も
`FuturesLossCarryforward`テーブルで上場株式等側(`InvestmentLossCarryforward`)
とは別に保持し、`/import`の専用セクションから登録・自動繰り越しができる。
`InvestmentAssetType`からは「FX」を削除した。

DMM FX・GMOクリック証券等の決済履歴CSVも`src/lib/investment/futuresCsv.ts`
から取り込める。業者ごとに様式が異なり未検証のため専用プリセットは用意せず、
暗号資産の証拠金取引CSV(`src/lib/crypto/marginCsv.ts`)と同様、決済日時・
銘柄・決済損益・手数料・スワップの列名を指定する汎用マッピング方式のみで
対応する。

### 15. パスワード認証 — `src/lib/auth/`・`src/proxy.ts`

暗号資産・投資の取引明細や損益額といった機微な情報を扱うため、自宅サーバー等
インターネットからアクセス可能な場所にホスティングする場合に備えて、単一パスワード
によるアクセス制御を追加できるようにした。`.env`に`AUTH_PASSWORD`(パスワード本体)
と`SESSION_SECRET`(セッションCookieの署名鍵。`openssl rand -base64 32`等で生成)を
設定すると有効化される。`AUTH_PASSWORD`が未設定の場合は従来通り認証なしで動作する
(ローカルのみで使う個人利用ではこれが既定)。

`AUTH_PASSWORD`との比較はタイミング攻撃対策として`node:crypto`の`timingSafeEqual`
で行う(`src/lib/auth/password.ts`)。ログイン成功時は`jose`で署名したJWT
(有効期限7日、`{authenticated: true}`のみを含む最小限のペイロード)を`httpOnly`・
`sameSite=lax`のセッションCookieとして発行する(`src/lib/auth/session.ts`)。ユーザー
アカウントという概念は持たない単一パスワードの仕組みのため、ユーザーIDやメール
アドレス等の個人情報はセッションに含まない。

認可チェックはNext.js 16の`proxy.ts`(旧Middleware)で行う(`src/proxy.ts`)。
`/login`と静的アセット以外の全リクエストに対してセッションCookieを検証し、
未認証であれば`/login`へリダイレクトする。ログイン画面・ログアウトボタンは
`src/app/login/`のServer Actionsで実装しており、ダッシュボードのヘッダーに
`AUTH_PASSWORD`設定時のみログアウトボタンを表示する。

総当たり攻撃対策として、IPアドレス単位でログイン失敗回数を制限する
(`src/lib/auth/loginRateLimit.ts`)。15分以内に5回失敗すると、直近の失敗時刻から
15分間そのIPアドレスからのログインを拒否する(ロック中にさらに失敗すると解除
時刻はその都度後ろにずれる)。失敗履歴は`LoginAttempt`テーブルに保持し、
ログイン成功時にそのIPアドレス分を削除するほか、ロック判定に不要になった古い
レコードも都度削除するため肥大化しない。プロキシ経由の接続元IPアドレスは
`X-Forwarded-For`(無ければ`X-Real-IP`)ヘッダーから取得するため、信頼できる
リバースプロキシ配下での運用を前提とする(ヘッダーを偽装できるインターネットに
直接公開する構成では、送信元IPアドレスの検証を別途行うこと)。

**制約:** ユーザーアカウント・権限管理を持たないシンプルな「サイト全体を1つの
パスワードで保護する」方式であり、複数人での利用は想定しない(ロードマップの
「認証・マルチユーザー対応」は引き続き今後の課題)。

### 16. 所得税・住民税の概算合計税額試算 — `src/lib/taxEstimate.ts`

暗号資産の雑所得・株式等の譲渡所得・配当所得・先物取引に係る雑所得等は、
それぞれ別の欄・別の税率でダッシュボードに表示されるため、確定申告全体で
最終的にいくら税金を納めることになるのかが分かりにくかった。`/tax-estimate`
では、これらすべてを合算し、その年の所得税・復興特別所得税・住民税の
概算合計額を1つの試算結果として表示する。

各所得区分の課税方式は次の通り: 暗号資産の雑所得は給与所得等(手入力)と
合算する総合課税(超過累進税率、`src/lib/incomeTax.ts`の速算表を使用)、
株式等の譲渡所得と先物取引に係る雑所得等はそれぞれ別プールの申告分離課税
(一律20.315%、両者は損益通算不可)、配当所得は総合課税・申告分離課税・
申告不要の3方式(`dividendTaxSimulation.ts`の試算結果を利用し、指定が
なければ最も有利な方式を自動選択、申告分離課税時は株式等の譲渡損失との
損益通算も反映)。株式等・配当・先物取引の各金額はその年の集計値を
初期値として表示するが、給与所得等の課税所得金額(所得控除後)は
本ツールが管理していないため手入力が必要。

配当所得の課税方式シミュレーション(機能6)・外国税額控除の試算(機能12)で
使っていた所得税の速算表・復興特別所得税率・住民税率・申告分離課税の
税率は`src/lib/incomeTax.ts`に共通化し、`dividendTaxSimulation.ts`も
これを参照するようリファクタリングした。住民税は所得割10%固定(均等割・
調整控除は含まない)、源泉徴収税額・予定納税額との相殺も行わないため、
実際の納付額・還付額とは異なる概算値である点は配当所得のシミュレーションと
同様。

### 17. 含み損益(未実現損益)シミュレーション — `src/lib/unrealizedGain.ts`

`/unrealized-gain`では、その年分にアプリへ登録した取引から計算した期末保有数量・
平均取得単価(暗号資産は`crypto/calculator.ts`、株式等は`investment/calculator.ts`が
既に計算している`closingQuantity`/`closingCostJpy`をそのまま利用)をもとに、
現在価格を入力すると銘柄ごとの含み損益と評価額を試算できる。時価データを自動取得する
仕組みは持たないため、現在価格は手入力が前提(初期値は平均取得単価=含み損益0円)。

年末までに売却(決済)した場合の損益をあらかじめ確認できるようにすることで、
損出し(含み損のある銘柄を年内に売却して当年の所得を圧縮する節税策)や利確の
タイミングを検討する材料を提供する。ただし資産区分によって売却損の使い道が
異なるため、含み損の銘柄には「損出し候補」バッジを表示しつつ、資産区分ごとの
注意点(暗号資産の雑所得は当年の暗号資産の雑所得内でしか通算できず繰越不可、
株式等の課税口座分は他の株式等の譲渡益・配当と通算でき繰越控除〈3年〉も使える、
NISA口座分は非課税のため含み損を実現しても損益通算できない)を明記する。
同一銘柄を複数の証券会社・取引所で保有している場合は合算して試算する点、
実際の約定単価・手数料・スワップ等は反映しない概算である点は他のシミュレーター
機能(配当所得の課税方式シミュレーション等)と同様の制約。

### 18. ふるさと納税(寄附金控除)の年間上限額試算 — `src/lib/furusatoNozei.ts`

暗号資産・株式等の利益が多い年ほど住民税所得割額が増え、ふるさと納税で
実質2,000円の自己負担のまま寄附できる年間上限額(控除上限額)も大きくなる。
`/tax-estimate`(所得税・住民税の概算合計税額試算)の試算結果に、総務省
「ふるさと納税ポータルサイト」が公表する速算式
(`特例控除額の上限(住民税所得割額×20%) ÷ (90% − 所得税の限界税率×1.021) + 2,000円`)
による年間上限額の目安を追加表示するようにした。住民税所得割額は
`estimateTotalTax`が計算する住民税合計額(所得割10%固定の概算)を、所得税の
限界税率は総合課税分の課税所得金額(配当所得を総合課税で申告する場合は
それも上乗せ)に対応する速算表の税率(`src/lib/incomeTax.ts`の
`marginalIncomeTaxRate`)をそれぞれ自動的に使用するため、追加の入力項目は無い。

**制約:** 住宅ローン控除等、本ツールが管理していない他の税額控除との兼ね合い
(控除しきれない所得税額がある場合に上限額が目減りする)は考慮しない。また
ワンストップ特例制度固有の要件(寄附先5自治体以内等)も考慮せず、確定申告・
ワンストップ特例のどちらでも共通の上限額の考え方のみを試算する。

### 19. 医療費控除額の試算 — `src/lib/medicalExpenseDeduction.ts`

暗号資産・投資と直接の関係は無いが、確定申告で最も一般的な所得控除の一つである
医療費控除の額を、国税庁の計算式(実際に支払った医療費の合計額 − 保険金等の
補填額 − (10万円と総所得金額等の5%相当額のいずれか少ない方)、上限200万円)
に基づいて試算できるようにした。`/medical-expense-deduction`から、医療費の
合計額・保険金等の補填額・総所得金額等を入力すると控除額をその場で計算する。
総所得金額等の初期値は、この年の暗号資産・株式等・配当・先物の集計値と、
本ツールが管理しない給与所得等の仮定値(500万円。`/tax-estimate`と同じ
既定値)を合算した金額を表示する。

**制約:** 医療費控除と選択制で併用できない「セルフメディケーション税制」
(特定一般用医薬品等購入費控除)は対象外。保険金等の補填額は、本来は
対象となった医療費の額を超えて他の医療費から差し引かない扱いが原則だが、
本ツールでは年間合計額同士の差し引きとして簡略化している。ここで求めた
控除額を他の試算画面(`/tax-estimate`等)の所得金額に反映する連携は
行っておらず、ユーザー自身が該当の入力欄から差し引く必要がある。

### 20. 生命保険料控除額の試算 — `src/lib/lifeInsuranceDeduction.ts`

ロードマップの「他の主要な所得控除への対応拡大」のうち、生命保険料控除に
対応した。生命保険会社発行の控除証明書に記載された年間払込保険料額を、
一般生命保険料・介護医療保険料・個人年金保険料の3区分ごとに、新制度
(2012年1月1日以後の契約)・旧制度(2011年12月31日以前の契約。介護医療
保険料区分には存在しない)に分けて`/life-insurance-deduction`へ入力すると、
国税庁の速算表に基づく所得税・住民税それぞれの控除額をその場で試算する。
区分に新旧両方の契約がある場合は、新制度分のみ・旧制度分のみ・新旧合算
(新制度の上限4万円/2.8万円が上限)のうち最も有利な金額を自動選択する。
3区分合計は所得税12万円・住民税7万円が上限。

**制約:** 医療費控除と同様、暗号資産・投資の計算エンジンとは独立した単体の
試算画面であり、他の試算結果(`/tax-estimate`等)への自動反映は行わない。
各区分の控除額は円未満の端数を切り捨てずDecimalの計算結果をそのまま返す
概算値。個人年金保険料は税制適格特約付きの契約を前提とし、区分の判定
(特約の有無)自体はユーザー自身が行う前提とする。社会保険料控除・
小規模企業共済等掛金控除(iDeCo)は引き続き今後の課題(ロードマップ参照)。

### 21. 小規模企業共済等掛金控除(iDeCo等)の試算 — `src/lib/smallBusinessMutualAidDeduction.ts`

ロードマップの「他の主要な所得控除への対応拡大」のうち、小規模企業共済等
掛金控除に対応した。iDeCo(個人型確定拠出年金)・小規模企業共済・
心身障害者扶養共済の年間掛金額を`/small-business-mutual-aid-deduction`へ
入力すると、その合計額(生命保険料控除等と異なり上限や速算表は無く、
支払った掛金の**全額**がそのまま所得税・住民税共通の控除額になる)を試算する。

iDeCoのみ、加入区分(自営業者等・会社員(企業年金なし/企業型DCのみ/DB等
併用)・公務員等・専業主婦(主夫)等)ごとに年間拠出限度額が法令で定められて
いるため、選択した区分の限度額を参考表示し、入力額がそれを超えている場合は
警告する(iDeCoの掛金は運営管理機関側で限度額超過拠出ができない仕組みのため、
主に年の途中で加入区分が変わった場合の入力ミス検知が目的で、超過していても
控除額の計算自体には影響させない)。DB(確定給付企業年金)等に加入している
会社員は、2024年12月の制度改正以降、限度額が勤務先のDB等の給付水準により
個人ごとに異なるため自動判定の対象外とし、運営管理機関からの通知で確認する
よう促すに留める。

**制約:** 他の単体試算画面と同様、暗号資産・投資の計算エンジンや
`/tax-estimate`等の他の試算結果への自動反映は行わない。国民年金基金の掛金・
国民年金の付加保険料(第1号被保険者の場合iDeCoと合算して年81.6万円が上限)は
本ツールの対象外(社会保険料控除の対象。機能22参照)。

### 22. 社会保険料控除額の試算 — `src/lib/socialInsuranceDeduction.ts`

ロードマップの「他の主要な所得控除への対応拡大」のうち、社会保険料控除に
対応した。国民年金保険料・国民年金基金の掛金・国民年金の付加保険料・
国民健康保険料・後期高齢者医療保険料・介護保険料・厚生年金保険料・雇用保険料・
その他の社会保険料の年間支払額を`/social-insurance-deduction`へ区分ごとに
入力すると、その合計額(小規模企業共済等掛金控除と同様、上限や速算表は無く
支払った金額の**全額**がそのまま所得税・住民税共通の控除額になる)を試算する。
納税者本人分だけでなく、生計を一にする配偶者その他の親族の社会保険料を本人が
支払った場合もその金額を含められる。

国民年金基金の掛金・国民年金の付加保険料は、小規模企業共済等掛金控除
(機能21・iDeCo等)ではなくこの社会保険料控除の対象という条文上の区分の違いを
明記した(iDeCoの年間拠出限度額の計算ではこれらを合算するが、所得控除としての
適用条文は別)。

**制約:** 他の単体試算画面と同様、暗号資産・投資の計算エンジンや
`/tax-estimate`等の他の試算結果への自動反映は行わない。給与から天引きされ
勤務先の年末調整で控除済みの厚生年金保険料・雇用保険料・健康保険料は通常
確定申告での追加入力が不要なため、本ツールはどのケースかを判定せず入力された
金額の合計をそのまま返す(年の途中の退職等、年末調整でカバーされない分の
入力を想定)。

### 23. 所得控除試算の登録と`/tax-estimate`への自動反映 — `src/lib/incomeDeduction.ts`

医療費控除(機能19)・生命保険料控除(機能20)・小規模企業共済等掛金控除
(iDeCo等。機能21)・社会保険料控除(機能22)の4つの試算画面は、これまで
それぞれ単体で完結しており、求めた控除額を他の試算画面(特に
`/tax-estimate`の「給与所得等の課税所得金額」)へ反映するにはユーザーが
手動で差し引く必要があった。各試算画面に「この試算結果を◯年分の所得控除
として登録する」ボタンを追加し、押すと`IncomeDeduction`テーブルへ
年分・控除区分ごとに保存する(区分ごとに1件、再登録すると上書き)。

`/tax-estimate`はこの年に登録済みの所得控除をすべて合算し、「給与所得等の
課税所得金額」の初期値を「仮の給与収入(500万円)− 登録済み控除合計額
(所得税ベース)」として表示するとともに、登録内容の内訳を参考表示する。
生命保険料控除は所得税と住民税とで速算表が異なり控除額が一致しないことが
あるため、区分によらず所得税用・住民税用の金額を別々に保存する(それ以外の
区分は同額を保存する)。医療費控除とセルフメディケーション税制(機能24)は
選択制で併用できないため、両方登録されている場合は`summarizeIncomeDeductions`が
所得税ベースの控除額が大きい方のみを合計に反映し、その旨の注記を
`/tax-estimate`に表示する。

**制約:** 基礎控除・配偶者控除・扶養控除等、この5区分以外の所得控除は
引き続き自動反映の対象外(ロードマップ参照)。「仮の給与収入500万円」は
実際の給与収入額とは無関係な固定値のプレースホルダーのため、初期値は
あくまで目安であり、実際の課税所得金額は必ずユーザー自身が確認して
入力欄を上書きすること。

### 24. セルフメディケーション税制との比較試算 — `src/lib/selfMedicationDeduction.ts`

医療費控除(機能19)と選択制で併用できない「セルフメディケーション税制」
(特定一般用医薬品等購入費控除。租税特別措置法41条の17)に対応した。
`/medical-expense-deduction`の医療費控除試算の下に、特定一般用医薬品等
(スイッチOTC医薬品等)の年間購入費・保険金等の補填額・健康の保持増進及び
疾病の予防への一定の取組(健康診断・予防接種等)の有無を入力する比較セクションを
追加し、セルフメディケーション税制の控除額(購入費の合計額 − 保険金等の補填額 −
12,000円、上限88,000円)を試算した上で、医療費控除とどちらが有利かを
`compareMedicalDeductionOptions`が判定して差額とともに表示する。

セルフメディケーション税制の試算結果も医療費控除と同様に「この年分の所得控除
として登録する」ボタンから`IncomeDeduction`(区分`SELF_MEDICATION`)へ登録できる。
両制度は法律上どちらか一方しか選べないため、医療費控除とセルフメディケーション
税制の両方が登録されている場合、`/tax-estimate`の合計額には有利な方のみを
反映し(機能23参照)、両方の金額が参考表示される。

**制約:** 「一定の取組」を行っているかどうかの実施判定自体はユーザーに委ね、
チェックが外れている場合は注記を表示するのみで計算式には影響させない
(取組を行っていない場合、控除額はあくまで参考値)。対象医薬品(スイッチOTC
医薬品等)かどうかの判定もユーザー自身が行う前提とする。

### 25. 配偶者控除・配偶者特別控除・扶養控除の試算 — `src/lib/dependentDeduction.ts`

ロードマップの「他の所得控除への対応拡大」のうち、基礎控除以外の人的控除である
配偶者控除・配偶者特別控除(所得税法83条・83条の2)・扶養控除(同法84条)に対応した。
`/dependent-deduction`から、納税者本人の合計所得金額・配偶者の有無と合計所得金額・
年齢(70歳以上かどうか)を入力すると、国税庁の速算表に基づき配偶者控除
(配偶者の合計所得金額48万円以下)または配偶者特別控除(48万円超133万円以下、
納税者本人の合計所得金額に応じて段階的に逓減)のいずれか該当する控除額を所得税・
住民税それぞれ試算する。扶養親族は「扶養親族を追加」ボタンで年齢・合計所得金額
(70歳以上の場合は同居老親等かどうか)を人数分入力でき、一般の控除対象扶養親族
(16〜18歳・23〜69歳、38万円/33万円)・特定扶養親族(19〜22歳、63万円/45万円)・
老人扶養親族(70歳以上、同居老親等58万円/45万円・それ以外48万円/38万円)に自動
区分して合算する(16歳未満は対象外)。他の所得控除試算画面と同様、それぞれ
「この試算結果を◯年分の所得控除として登録する」ボタンから`IncomeDeduction`
(区分`SPOUSE`・`DEPENDENT`)へ登録でき、`/tax-estimate`の「給与所得等の課税所得金額」
の初期値に自動反映される。

令和7年度税制改正(いわゆる「103万円の壁」対応)のうち、扶養親族・同一生計配偶者の
合計所得金額要件(48万円→58万円)の変更は年分に応じて自動的に切り替わる(`year`が
2025年分以後なら58万円、2024年分以前なら48万円を適用)。配偶者特別控除は上限
(133万円)・控除額の段階表自体に変更は無く、この要件緩和(対象範囲が58万円超〜に
変わる)の反映のみで対応できている。

**制約:** 令和7年度税制改正のうち、基礎控除の引き上げ(所得金額に応じた段階表への
変更)と、19〜22歳の親族向けに新設された「特定親族特別控除」は未対応。これらは
控除額の段階表(国税庁の速算表)を一次情報で確実に確認できておらず、本ツールの
他の機能と同様に未検証の値を誤って組み込むリスクを避けるため、安全側に倒して
見送った。該当する場合は国税庁「確定申告書等作成コーナー」の最新の控除額で
別途計算すること。配偶者控除・扶養控除の適用要件(生計を一にする、青色事業専従者等
でない等)の判定自体はユーザーに委ね、本ツールは入力された所得金額・年齢からの
控除額算出のみを行う。

### 26. マネーフォワード資産残高突合の評価額比較(現在価格の手入力) — `src/lib/moneyforward/assetBalanceReconciliation.ts`

ロードマップの「マネーフォワード資産残高突合の評価額比較」に対応した。時価を
自動取得する仕組みは持たないため、`/import`の「現在価格(時価)の登録」欄から
銘柄シンボルごとに現在価格(1単位あたり・円)を手入力で登録する方式にした
(`MarketPrice`テーブル。年に紐付かない全年共通のマスタデータ)。

登録すると、「銘柄単位の突合」表に「評価額突合」列が追加され、その銘柄の
期待保有数量(期首残高+当年の取引による増減。数量突合(機能11)と同じ計算)
×登録価格を期待評価額として、マネーフォワード側の評価額(残高)と比較する。
手入力の価格はマネーフォワード側の評価時点と必ずしも一致しないため、完全一致は
求めず、期待評価額との差が±10%を超える場合のみ「評価額乖離大(要確認)」として
警告する目安情報にとどめる(一致していても計上漏れが無いことを保証しない)。
数量突合とは異なりCSVに数量列(quantityColumn)が無くても計算できる
(期待保有数量自体はCSVの数量列に依存しないため)。期首残高が複数の金融機関に
またがり按分できない銘柄は、数量突合と同様に判定を見送る。

この現在価格の登録は`/unrealized-gain`(含み損益シミュレーション)とも連携し、
登録済みの銘柄は現在価格欄の初期値としてそのまま使われる(未登録の銘柄は
従来どおり平均取得単価が初期値になる)。

### 27. NISA生涯投資枠(総枠1,800万円)の使用状況試算 — `src/lib/investment/nisaQuota.ts`

機能13(NISA年間投資枠)で対象外としていた生涯非課税限度額(総枠1,800万円・
うち成長投資枠1,200万円)を試算できるようにした。生涯投資枠は過去の買付・
売却の累積(簿価残高)を追う必要があり、売却により再利用可能になった枠は
売却した年の翌年からしか使えないため、年間投資枠のようにその年の取引だけでは
判定できない。そこで`/import`の「NISA生涯投資枠」セクションから、枠区分
(つみたて投資枠/成長投資枠)ごとに、その年の年始時点で確定している非課税枠
使用額(前年末時点の保有簿価残高)を`NisaLifetimeQuota`テーブルへ手入力できる
ようにした。「前年分の計算結果から自動で繰り越す」ボタンで前年分の当年末使用額
(年始使用額+前年買付-前年売却簿価)をそのまま当年の年始使用額として一括登録
できる(既に登録済みの枠区分は上書きしない)。

当年の買付額は取引明細(NISA枠区分を指定して登録した買付)から自動集計するが、
当年中に売却した保有分の取得価額(簿価)は本ツールのデータだけでは自動追跡
できないため(平均取得単価をNISA枠区分ごとに分けて管理していない)、
`soldCostBasisJpy`欄への手入力に頼る簡略化とした(未入力の場合は0として扱う)。
この売却簿価は翌年に戻る枠の額(=当年末使用額=翌年への繰越額)の算出にのみ
使い、当年の買付が年始時点の残り枠を超えていないかの判定には影響しない
(枠の再利用は売却した年の翌年からのため)。ダッシュボードには当年末時点の
使用額・残枠を総枠/成長投資枠別に表示し、年始時点の残り枠を超える買付が
あった場合は警告表示する。

### 29. 地震保険料控除額の試算 — `src/lib/earthquakeInsuranceDeduction.ts`

損害保険会社発行の控除証明書の年間払込保険料額から、地震保険料控除額を試算できる
ようにした(`/earthquake-insurance-deduction`)。地震保険料(所得税は全額・上限5万円、

### 32. 雑損控除額の試算 — `src/lib/casualtyLossDeduction.ts`

国税庁タックスアンサーNo.1110の計算式に基づき、災害・盗難・横領により住宅家財等の
生活用資産に損害を受けた場合の雑損控除額を試算できるようにした
(`/casualty-loss-deduction`)。他の所得控除試算画面の中で唯一未対応だった項目
(ロードマップ参照)。

差引損失額(損害金額+災害等関連支出の金額-保険金等により補填される金額。
保険金等はまず損害金額に優先充当し、残額を災害関連支出に充当)を算出したうえで、
控除額は次のいずれか多い方を採用する:

1. 差引損失額 - 総所得金額等×10%
2. 差引損失額のうち災害関連支出の金額 - 5万円

所得税・住民税とも同一の算式(地方税法上も国税と同じ計算方法)のため、
この試算では控除額を同額として扱う。他の所得控除試算画面と同様、
`IncomeDeduction`テーブルの`CASUALTY_LOSS`区分として登録でき、`/tax-estimate`の
初期値・下書きCSVの所得控除サマリーに自動反映される。控除しきれなかった金額を
翌年以後3年間繰り越せる「雑損失の繰越控除」は機能33で対応した。損害金額の算定方法
自体の自動化(資産の時価の自動取得等)は引き続き未対応(今後の課題)。

### 33. 雑損失の繰越控除(3年間) — `src/lib/casualtyLossCarryforward.ts`

機能32(雑損控除)の控除額がその年の総所得金額等を超えて控除しきれなかった場合、
その超過額(雑損失の金額)を翌年以後3年間繰り越して総所得金額等から控除できる
「雑損失の繰越控除」(所得税法71条)に対応した。上場株式等の譲渡損失の繰越控除
(`InvestmentLossCarryforward`)と同様、`CasualtyLossCarryforward`テーブルに
発生年ごとの繰越残高を保持し、発生年の古い順に当年の総所得金額等から控除する。

雑損控除は特定の所得区分ではなく総所得金額等全体に対する控除であるため、当年
新たに発生した雑損控除額(総所得金額等による上限をかける前の金額)と、前年以前
からの繰越雑損失の両方が同じ年の同じ所得枠を奪い合う点が、譲渡損失の繰越控除
(その年の譲渡益という単一の枠のみ)と異なる。本ツールでは、期限切れが近い
(発生年が古い)繰越雑損失を優先してその年の総所得金額等に充当し、なお残った
枠を当年発生分に充てる実装とした(当年発生分は翌年以後3年間使えるのに対し、
古い繰越分は期限が迫っているため)。この充当順序は条文上明記されているわけ
ではなく、実装上の判断である点に注意。

`/casualty-loss-deduction`の試算画面に、年初時点の繰越雑損失残高(発生年ごと。
登録・削除は`/import`の「雑損失の繰越控除」セクション)を加味した「実際にその年の
総所得金額等から控除できる合計額」を表示し、この金額(繰越控除の使用額+当年分の
適用額)を`IncomeDeduction`の`CASUALTY_LOSS`区分として登録する方式に変更した
(従来は総所得金額等による上限を考慮しない金額をそのまま登録していた)。控除
しきれず翌年以後に繰り越す新規の雑損失額が発生した場合は、外国税額控除の繰越
(`/foreign-tax-credit`)と同様、雑損控除の計算に必要な損害金額・総所得金額等が
DBに保存されない都度入力のため、試算画面から直接翌年分として一括登録するボタンを
用意した。

### 34. 暗号資産取引所CSV手動マッピング欄の入力補助(列見出し・売買値の候補一覧) — `src/lib/crypto/exchangeCsv.ts`

`/import`の「暗号資産取引所CSVの取り込み」で「その他 / 手動マッピング」を選んだ際、
自動認識(機能4参照)が失敗すると列名を1件ずつ手入力する必要があったが、
何を入力すればよいか(実際のCSVのヘッダー行の表記に対して、どんな候補が
認識されるか)が分かりづらかった。日付・銘柄・売買種別・数量・単価・手数料の

(`COMMON_EXCHANGE_CSV_TRADE_TYPE_VALUES`)を表示することで、実際のCSVの
表記と見比べながら選べるようにした。ネイティブHTMLの`<datalist>`による
入力補助のため追加のJavaScriptは不要で、自由入力(候補にない列名)も
引き続き可能。あわせて、自動認識が失敗した際のエラーメッセージが不足カラムを
`date`/`pair`等の内部キーのままユーザーに表示していた不具合も、日本語ラベルに
修正した。実データに基づくプリセット拡充自体は引き続き今後の課題
(ロードマップ参照)。

### 37. 証券会社の特定口座年間取引報告書のテキスト貼り付け取り込み — `src/lib/investment/annualReportText.ts`

機能9(証券会社の特定口座年間取引報告書との突合)の登録は、これまで金額を
1件ずつ手入力するか、専用プリセットのないCSVを用意する必要があった。
年間取引報告書自体はPDFで発行される証券会社が多く、本ツールはPDFファイル
そのもののレイアウト解析・OCRには対応しない(証券会社ごとの様式差異が大きく、
画像化された(テキスト層のない)PDFも存在するため)。そのため、PDFビューアで
本文をコピーしたテキスト(またはテキストとして保存した内容)を`/import`の
テキストエリアに貼り付けると、国税庁の様式(租税特別措置法施行規則)で
証券会社によらず共通の文言である「譲渡の対価の額(収入金額)」「取得費及び
譲渡に要した費用の額等」「差引金額(譲渡所得等の金額、参考表示のみ)」
「配当等の額」のラベルを手がかりに金額を読み取り、下書きとして画面に表示する
方式にした。証券会社名・口座区分(源泉徴収の有無等)についても文中の文言から
推測を試みるが、レイアウトの揺れにより確実ではないため、あくまで下書きであり
「反映する」ボタンを押すまで入力欄には反映されない。反映後も登録前に必ず
内容を確認・修正できる(全角数字・全角括弧・全角スペースはNFKC正規化で吸収し、
差引金額が「▲」「△」付きの損失表記であってもマイナス値として解釈する)。
既存のCSV取り込み・手入力欄はそのまま残しており、この機能はあくまで
入力の下書きを高速化する補助である。

### 38. 住宅借入金等特別控除(住宅ローン控除)の試算 — `src/lib/mortgageDeduction.ts`

これまでの所得控除試算画面群(医療費控除・生命保険料控除等)とは異なり、
住宅ローン控除は所得税額から直接控除する税額控除のため、`IncomeDeduction`

### 39. 住宅ローン控除の床面積40㎡以上50㎡未満の特例 — `src/lib/mortgageDeduction.ts`

機能38(住宅ローン控除)のロードマップで未対応としていた「床面積40㎡以上50㎡
未満の特例」(租税特別措置法41条11項)に対応した。新築等(既存住宅・買取
再販住宅を除く)の住宅で床面積が40㎡以上50㎡未満の場合、通常は床面積50㎡
以上でなければ住宅ローン控除の対象にならないところ、合計所得金額が1,000万円
以下の年に限り控除の対象になる(通常の合計所得金額要件2,000万円より厳しい)。
`/mortgage-deduction`の「床面積40㎡以上50㎡未満の特例」にチェックを入れると、
この年の合計所得金額の判定に使う上限額が2,000万円ではなく1,000万円に
切り替わる(借入限度額・控除期間の判定は変わらない)。既存住宅(中古)に
チェックが入っている場合はこの特例の対象外である旨を注記表示し、通常の
2,000万円要件のまま計算する。

**制約:** この特例の対象となるには本来、住宅の建築確認を一定の期限までに
受けている必要があるが、その期限について複数の情報源を確認したところ
「令和5年12月31日」とする情報と「令和6年度税制改正で延長された」とする
情報の両方があり、本ツールの他の機能と同様に未検証の値を誤って組み込む
リスクを避けるため一次情報で確実に確認できなかった。そのため期限の判定
自体は行わず、合計所得金額の要件判定のみを反映し、対象年分に該当するかは
ユーザー自身が確認する前提とした。

### 40. 住宅ローン控除の`/tax-estimate`統合(税額控除としての自動反映) — `src/lib/taxEstimate.ts`

機能38・39の住宅ローン控除は独立した試算専用ページ(`/mortgage-deduction`)の
みで完結しており、`/tax-estimate`の合計税額試算には反映されていなかった
(ロードマップで「今後の課題」としていた点)。`/mortgage-deduction`に
「この試算結果を◯年分の住宅ローン控除として登録する」ボタンを追加し、
所得税分・住民税分の控除額を`MortgageDeductionRecord`テーブルへ年分ごとに
保存できるようにした。`/tax-estimate`はこの登録値を初期値として税額控除の
入力欄に反映し、`estimateTotalTax`が算出した合計税額(所得税・復興特別所得税・

性質が異なり所得金額ではなく税額そのものから控除するため、`IncomeDeduction`
とは別のテーブル・別の計算経路として実装した。控除額がその年の税額を

住宅ローン控除適用前の住民税所得割額を基準とする従来の計算を維持しており、
住宅ローン控除による変動は含めていない(実際の限度額計算での位置づけは
より複雑なため、既存の簡略化を踏襲した)。

### 41. 住宅ローン控除の連帯債務(共有名義)の持分按分 — `src/lib/mortgageDeduction.ts`

機能38〜40のロードマップで「今後の課題」としていた、連帯債務(共有名義)で

金額を事前に手計算してから入力する前提だったが、`/mortgage-deduction`に
「連帯債務(共有名義)の持分按分を行う」チェックボックスを追加し、これを
有効にすると年末借入金残高の入力欄が「連帯債務者全員分の合計額」の意味に
切り替わり、あわせて入力する「本人の債務負担割合(%)」を乗じた金額を
本人の年末借入金残高として自動計算する(国税庁タックスアンサーNo.1234)。
負担割合は連帯債務者間の合意で定める割合(実務上は持分登記割合・出資割合と
一致させることが多い)で、この判定自体は従来通りユーザー自身が行う前提とする。
按分後の本人の年末借入金残高は試算結果にも表示し、以降の借入限度額との比較・
控除額計算はこの按分後の金額を用いる。取得価額に対する持分割合との整合性
(借入金が取得価額の持分相当額を超える場合の特殊な取り扱い)は未対応で、
引き続き今後の課題とする(ロードマップ参照)。

### 42. 住宅ローン控除「その他の住宅」の経過措置(令和6・7年入居) — `src/lib/mortgageDeduction.ts`

ロードマップで「今後の課題」としていた、新築等の「その他の住宅」(省エネ基準への
適合なし)で令和6・7年(2024・2025年)に入居した場合の経過措置に対応した。この
制度区分は原則、令和6年以降に入居すると住宅ローン控除の対象外(借入限度額0円)に
なるが、令和5年12月31日までに建築確認を受けた場合、または令和6年6月30日までに
建築された場合は、経過措置として借入限度額2,000万円・控除期間10年(令和4・5年
入居の「その他の住宅」の水準よりは低いが対象外にはならない)で控除を受けられる。
複数の独立した税理士法人・不動産関連メディアの解説記事で数値が一致することを
確認した上で実装した。

`/mortgage-deduction`で住宅の区分を「その他の住宅」、居住を開始した年を2024年
または2025年、既存住宅(中古)のチェックを外した状態にすると、経過措置の対象か
どうかを選べるチェックボックスが表示される。建築確認日・建築日がこの期限内で
あるかどうかの判定自体は、床面積40㎡以上50㎡未満の特例(機能39)と同様に本ツールでは
行わないため、ユーザー自身が確認する前提とする。子育て世帯等向けの上乗せ措置・
床面積特例とは独立した条件のため、併用時の判定にも影響しない
(子育て世帯等の上乗せは「その他の住宅」自体が対象外のため引き続き適用されない)。

### 43. 源泉徴収税額を考慮した納付・還付見込み額の試算 — `src/lib/taxEstimate.ts`

`/tax-estimate`の合計税額試算はこれまで「その年の税額そのものの概算値」しか
求められず、給与や配当・特定口座内の株式等譲渡益等で既に源泉徴収(特別徴収)
された税額との差額(結局いくら納付・還付になるのか)は自分で暗算する必要が
あった。既に源泉徴収された所得税・復興特別所得税の合計額
(`withheldNationalTaxJpy`)と、特定口座(源泉徴収あり)内の株式等譲渡益・配当等に
ついて証券会社が徴収した住民税相当額(通常5%)の合計額(`withheldResidentTaxJpy`)
の2つを追加入力すると、それぞれの税額との差額を「納付見込み額(正の値)」
「還付見込み額(負の値)」として試算する。未入力(0円)の場合は従来通り年間の
税額そのものの概算値のみを表示する。

**制約:** 所得税分は確定申告により還付・追加納付が生じる一般的な仕組みだが、
特定口座(源泉徴収あり)内の住民税相当額は所得税と異なり、確定申告時にその場で
還付されるものではなく、翌年度の住民税(特別徴収・普通徴収)の額に反映される
形で精算される。そのため住民税分の「納付・還付見込み額」はあくまで概算の
目安であり、実際の精算時期・方法とは異なる点に注意する。予定納税額との相殺は
引き続き行わない。

### 44. 住宅ローン控除の令和8年(2026年)〜令和12年(2030年)入居分への対応 — `src/lib/mortgageDeduction.ts`

ロードマップで「一次情報での確認不足」を理由に見送っていた、令和8年度税制改正
(令和7年12月19日与党公表)による住宅ローン控除の見直しに対応した。国土交通省の
公表資料(「令和8年度住宅税制改正概要」PDF、および住宅ローン減税特設ページの
新築住宅・既存住宅それぞれの区分別ページ)を直接参照し、区分ごとの借入限度額・
控除期間を確認した上で実装した。

- 令和8年(2026年)〜令和12年(2030年)入居分は次のとおり(住宅ローン減税を
  5年間延長)。
  - 新築等の認定長期優良住宅・認定低炭素住宅(CERTIFIED): 4,500万円
    (子育て世帯等5,000万円)・控除期間13年間。
  - 新築等のZEH水準省エネ住宅(ZEH): 3,500万円(子育て世帯等4,500万円)・
    控除期間13年間。
  - 新築等の省エネ基準適合住宅(ENERGY_SAVING): 令和8・9年(2026・2027年)入居分は
    2,000万円(子育て世帯等3,000万円)・控除期間13年間。令和10年(2028年)以降
    入居分は原則対象外(借入限度額0円)になるが、令和9年(2027年)末までの建築確認
    (または令和10年6月30日までの建築)があれば、経過措置(`energySavingTransitionalMeasure`)
    として借入限度額2,000万円・控除期間10年(子育て世帯等の上乗せなし)の対象になる。
  - 新築等の「その他の住宅」は引き続き原則対象外だが、機能42の経過措置
    (`otherHousingTransitionalMeasure`)は入居年を問わず建築確認日・建築日の期限
    のみで判定されることを国土交通省の公表資料で確認したため、令和8年以降入居分
    にも同じ経過措置を適用できるようにした。
  - 既存住宅(中古)は令和4〜7年入居分(区分によらず一律の限度額・控除期間10年、
    子育て世帯等の上乗せなし)と異なり、住宅の区分ごとに新築等に近い枠組みが
    導入される。認定長期優良住宅・認定低炭素住宅・ZEH水準省エネ住宅は3,500万円
    (子育て世帯等4,500万円)、省エネ基準適合住宅は2,000万円(子育て世帯等
    3,000万円)、いずれも控除期間13年間に拡充。「その他の住宅」は従来どおり
    2,000万円・控除期間10年(子育て世帯等の上乗せなし)。既存住宅への子育て
    世帯等向け上乗せ措置は令和8年度税制改正で新設された措置である。
  - 床面積要件は「50㎡以上」から「40㎡以上」へ恒久的に緩和される(期限付きの
    建築確認要件は撤廃)。ただし合計所得金額が1,000万円を超える場合、または
    子育て世帯等向けの上乗せ措置を利用する場合は引き続き50㎡以上が必要なため、
    令和8年以降入居分で床面積40㎡以上50㎡未満の特例(`isSmallFloorArea`)と
    子育て世帯等(`isChildRearingHousehold`)をともに指定した場合は要件を
    満たさないものとして適用対象外(eligible=false)を返す。

**制約:** 令和10年(2028年)以降入居分の新築住宅は、土砂災害特別警戒区域等の
「災害レッドゾーン」に所在する場合は住宅ローン控除の対象外になるが、この判定
(所在地の該当有無)は行わないため、該当の可能性がある場合はユーザー自身が
確認する前提とする(試算結果の注記に表示)。「買取再販住宅」固有の限度額差異は
従来どおり新築住宅と同じ限度額として扱う。

### 45. 配当所得の課税方式シミュレーションの配当控除率を銘柄種別ごとに区分 — `src/lib/investment/dividendTaxSimulation.ts`・`src/lib/investment/calculator.ts`

機能6(配当所得の課税方式シミュレーション)は、これまで配当控除率を上場株式
(普通配当)の税率(国税10%/5%・住民税2.8%/1.4%)一本で計算しており、
株式投資信託の分配金(本来は半分の税率)や公社債投資信託・J-REIT等の分配金
(本来は配当控除の対象外)が混在すると控除額を過大に試算する問題があった
(モジュール冒頭のコメントで既知の簡略化として明記されていたもの)。

`InvestmentTrade`には元々`assetType`(STOCK/ETF/MUTUAL_FUND/BOND/OTHER)が
登録されていたため、これを配当控除の3税率区分に対応させた
(`src/lib/investment/calculator.ts`の`dividendCreditCategory`)。

- STOCK・ETF: 通常税率(上場株式等の普通配当として扱う)。
- MUTUAL_FUND: 半分税率(外貨建資産等の組入割合が50%以下であることを前提と
  する簡略化。組入割合が50%超の場合はさらに率が下がるため、実際の控除額が
  試算値を下回る可能性がある)。
- BOND・OTHER: 配当控除の対象外(0%)。

`calculateInvestmentPortfolioYear`が課税口座分の配当等をこの3区分ごとに
自動集計する(`totalDividendFullCreditJpy`/`totalDividendHalfCreditJpy`/
`totalDividendNoCreditJpy`)ようになり、`/dividend-simulation`では区分ごとの
内訳(半分税率・対象外の2欄。残りは通常税率として扱う)を`/import`の登録済み
取引から自動集計した値を初期値として表示し、手入力でも上書きできる。
複数税率区分が混在する場合、1,000万円の合計所得金額の枠は通常税率の分から
優先して消費し、残りを半分税率の分に充てる(条文上の充当順序が明記されている
わけではない実装上の判断。対象外の分は枠を消費しない)。ETFのうちJ-REIT型
(本来は配当控除の対象外)を区別する銘柄種別の細分化は引き続き対象外。

### 46. マネーフォワード資産残高突合の「計上漏れの疑い」をダッシュボードに表示 — `src/lib/reporting.ts`・`src/app/page.tsx`

機能11(マネーフォワード資産残高との突合)の「計上漏れの疑い」判定
(`MISSING_APP_TRADES`。マネーフォワード側に残高がある金融機関なのに、
アプリに同じ名前の取引明細が1件も登録されていない)は、これまで`/import`
ページの一覧表でしか確認できず、`/import`を開かない限り気付けなかった。
確定申告の提出直前に見落とすと計上漏れにつながるため、`buildYearReport`
(トップページのダッシュボードが呼び出す集計関数)が`reconcileAssetBalances`
(機能11で実装済みの、DBに依存しない突合ロジックをそのまま再利用)を呼び出し、
その年に「計上漏れの疑い」となる金融機関が1件以上あれば、他の繰越控除の
注意喚起と同様にダッシュボード上部へ警告として表示するようにした。

マネーフォワード側に残高が無い、またはCSVを取り込んでいない年は警告は
表示されない。計上漏れとは限らない参考情報である旨は`/import`ページの
説明と同じ注記を添えている。逆方向(アプリには取引明細があるがマネー
フォワード側の残高に見当たらない`MISSING_IN_MONEYFORWARD`)は、資産移管等
でも起こりうる参考情報のため、従来通り`/import`ページでのみ確認する
運用のままとした(ダッシュボードで警告表示すると資産移管のたびに
無関係な警告が出続けてしまうため)。

### 47. 下書きCSVへの住宅ローン控除(税額控除)欄の追加 — `src/lib/etax/summary.ts`・`src/lib/etax/csvExport.ts`

機能10の下書きCSVはこれまで所得控除(`IncomeDeduction`)のみを転記対象と
しており、`/mortgage-deduction`で登録済みの住宅ローン控除額(税額控除。
`MortgageDeductionRecord`)は下書きCSVに含まれず、ユーザーが`/tax-estimate`
の画面を別途参照して転記する必要があった。`buildTaxFilingSummary`が
`MortgageDeductionRecord`の所得税控除額・住民税控除額を受け取れるように拡張し、
値があれば下書きCSVに「■ 税額控除(住宅ローン控除)」欄として、申告書第一表の
税額控除欄・(特定増改築等)住宅借入金等特別控除額の計算明細書への記載箇所と
ともに出力するようにした。住宅ローン控除が未登録の年は従来通りこの欄自体を
出力しない。

外国税額控除は、計算に必要なその年の所得税額等がDBに保存されない都度入力の
試算(`/foreign-tax-credit`)のため、今回は対象に含めていない(引き続き

### 48. 外国税額控除の当年分試算結果のDB永続化と下書きCSVへの反映 — `src/lib/investment/foreignTaxCredit.ts`・`src/lib/etax/summary.ts`・`src/lib/etax/csvExport.ts`

機能47で下書きCSVに住宅ローン控除(税額控除)を追加した際、外国税額控除
(`/foreign-tax-credit`)は当年の所得税額・所得総額等が都度入力の試算のまま
DBに保存されておらず、下書きCSVへの自動反映ができていなかった(ロードマップの
「外国税額控除の当年分試算結果のDB永続化」)。`MortgageDeductionRecord`に
倣い、年分ごとに1件保持する`ForeignTaxCreditRecord`テーブル(合計控除額
`totalCreditJpy`のみを保持)を追加し、`/foreign-tax-credit`の試算結果画面に
「この年分の外国税額控除として登録する」ボタンを追加した。登録すると
`buildTaxFilingSummary`が`ForeignTaxCreditRecord`を受け取れるようになり、
下書きCSVの「■ 税額控除」欄に住宅ローン控除と合算して、申告書第一表の
税額控除欄・外国税額控除に関する明細書への記載箇所とともに出力される
(未登録の年は従来通り「登録されていない」旨の注記のみ出力する)。

外国税額控除は所得税・復興特別所得税・住民税の3つの限度額に対して合計額のみを
充当する制度のため、当初は住宅ローン控除のように所得税分・住民税分を分けて
保存していなかった(実際の充当順序は確定申告書等作成コーナー側の計算に委ねる
前提だった)。この所得税分・住民税分への分割自体は機能50で対応した。
また繰越控除額(限度超過額・控除余裕額)は従来通り`ForeignTaxCreditCarryforward`/
`ForeignTaxCreditSpareLimitCarryforward`で別途管理する(今回の変更対象外)。

### 49. 予定納税額を考慮した納付・還付見込み額の試算 — `src/lib/taxEstimate.ts`

機能43で源泉徴収税額を考慮した納付・還付見込み額の試算に対応した際、
「予定納税額との相殺は引き続き行わない」注記付きで対象外としていた
(README各所で繰り返し言及されていた既知の制約)。事業所得等が一定額を
超える場合に前年の所得・税額を基準として7月・11月に前払いする予定納税額
(所得税・復興特別所得税のみの制度で住民税には存在しない)の合計額
(`estimatedTaxPrepaymentJpy`)を`/tax-estimate`に追加入力すると、源泉徴収税額と
合わせて所得税・復興特別所得税の納付・還付見込み額からさらに差し引くように
した。住民税分の納付・還付見込み額には影響しない。

**制約:** 予定納税の減額申請(業績悪化等による第1期・第2期の減額)や、
延滞税・加算税等の付帯税は考慮しない。あくまで通知書または実際に納付した
金額をそのまま入力する前提の単純な差し引き計算である。

### 50. 外国税額控除の`/tax-estimate`統合(税額控除としての自動反映) — `src/lib/investment/foreignTaxCredit.ts`・`src/lib/taxEstimate.ts`

機能48で外国税額控除の当年分試算結果をDBに永続化した際、住宅ローン控除とは
異なり`/tax-estimate`の合計税額試算への自動反映は「所得税・復興特別所得税・
住民税の3限度額にまたがる制度で単純に統合できない」ことを理由に対象外として
いた(ロードマップ参照)。

実際の外国税額控除は所得税→復興特別所得税→住民税の順に適用される
(`/foreign-tax-credit`の注記にも明記済み)ため、`calculateForeignTaxCredit`の
戻り値`totalCreditJpy`(合計控除額)をこの順序に従って機械的に振り分け、
`nationalTaxCreditJpy`(所得税・復興特別所得税から控除される額。所得税の
限度額+復興特別所得税の限度額までを上限とする)と`residentTaxCreditJpy`
(その残りで住民税から控除される額)に分割した。`totalCreditJpy`は当年発生分・
繰越控除限度超過額・繰越控除余裕額のいずれから充当されたかに関わらず
`totalLimitJpy`(3限度額の合計)を超えないため、この振り分けで住民税分が
住民税の限度額を超えることは無い。

`ForeignTaxCreditRecord`テーブルに`nationalTaxCreditJpy`/`residentTaxCreditJpy`
の2列を追加し(既存レコードは既定値0円)、`/foreign-tax-credit`の登録ボタンから
`totalCreditJpy`と合わせて保存するようにした。`/tax-estimate`は
`getMortgageDeductionRecord`と同様に`getForeignTaxCreditRecord`を呼び、
住宅ローン控除を適用した**後**の所得税額・住民税額からさらに外国税額控除を
差し引く(住宅ローン控除→外国税額控除の順で適用。両者とも控除額が残りの
税額を上回る場合は0円が下限で還付は生じない)。下書きCSVは従来通り
`totalCreditJpy`(合計額)のみを出力するため変更していない。

### 51. 住民税の均等割を合計税額試算に反映 — `src/lib/taxEstimate.ts`

これまでの合計税額試算(機能16)は住民税を所得割10%固定でのみ計算しており、
所得金額にかかわらず定額で課される均等割(道府県民税・市町村民税・森林環境税
(国税だが均等割とあわせて市区町村が徴収)の合計)が住民税額に含まれていな
かった。均等割の標準税率は年5,000円程度で長年変わっていないが、自治体が
独自の超過課税を行っている場合は上乗せされることがあり、住所情報を扱わない
本ツールでは自治体ごとの正確な金額を自動算出できない。

そのため、他の任意入力項目(源泉徴収税額・予定納税額)と同様に、ユーザーが
前年の住民税決定通知書等で確認した金額を`residentTaxPerCapitaLeviesJpy`として
入力できるようにし、入力があった場合のみ合計住民税額に加算する方式とした
(未入力時は従来通り所得割のみの概算値)。均等割は所得割と異なり住宅ローン
控除・外国税額控除等の税額控除の対象にならないため、それらの控除適用後の
住民税所得割額にそのまま加算する。また、ふるさと納税の上限額試算
(`furusatoNozei.ts`)は制度上住民税所得割額のみを基準とするため、均等割は
その基準額には含めていない。住民税の調整控除は、令和7年度税制改正による
基礎控除の段階表への変更に伴い所得税・住民税の人的控除額の差の再計算が
必要で一次情報での確認ができていないため、引き続き対象外としていたが、
機能52で対応した。

### 52. 住民税の調整控除の試算 — `src/lib/residentTaxAdjustmentDeduction.ts`・`/resident-tax-adjustment-deduction`

ロードマップで一次情報での確認不足を理由に見送っていた調整控除(地方税法
附則3条の3等。税源移譲に伴う所得税・住民税の人的控除額の差に基づく負担増を
住民税の所得割額から控除する制度)に対応した。

令和7年度税制改正(機能28)で所得税の基礎控除が合計所得金額に応じた段階表に
変わったことに伴い、基礎控除の人的控除額の差(従来は所得税48万円-住民税43万円の
一律5万円)も段階表に応じて再計算する必要があった。洲本市の公式ページ
(「個人市県民税の税額控除(令和8年度課税以降適用)」)で、合計所得金額336万円以下は
「税制改正後に新たな負担増が生じることがないことから、税制改正前の人的控除差
5万円をそのまま引き継ぐ」経過措置により5万円に据え置かれ、336万円超655万円以下は
所得税・住民税の基礎控除額の単純な差額(25万円/20万円/15万円)がそのまま人的控除額の
差になることを確認した。基礎控除以外の人的控除額の差(配偶者控除・扶養控除・
障害者控除・寡婦控除・ひとり親控除・勤労学生控除)についても同ページの一覧表が、
`src/lib/dependentDeduction.ts`・`src/lib/disabilityDeduction.ts`・
`src/lib/widowSingleParentDeduction.ts`で機能25・機能30・機能31としてそれぞれ
独立に国税庁タックスアンサー等を出典として実装済みの所得税・住民税控除額から
機械的に計算できる差額と完全に一致することをもって内容の正確性を確認した
(複数の独立した情報源での突き合わせという既存の確認方針に、独自実装済みの値との
突き合わせという方法を追加したもの)。配偶者特別控除・特定親族特別控除(いずれも
令和7年度税制改正関連)は人的控除額の差の対象に含まれない点、ひとり親控除は
旧寡婦(夫)控除からの沿革により父母で人的控除額の差が異なる(父1万円・母5万円)点も
同ページで確認した。

試算画面では、納税者本人の合計所得金額・合計課税所得金額(課税総所得金額等の
合計)と、各種人的控除の該当状況(配偶者控除の区分・扶養控除の区分ごとの人数・
障害者控除の区分ごとの人数・寡婦控除/ひとり親控除の区分・勤労学生控除の該当有無)を
入力すると、人的控除額の差の合計額と調整控除額を試算できる。他の所得控除試算画面群
(住宅ローン控除・外国税額控除等)とは異なり住民税のみに適用される税額控除のため、
`IncomeDeduction`テーブルへの登録は行わない独立した試算画面とした。市民税・道府県民税
(3%/2%)の内訳は、本アプリが住民税を所得割10%固定の単一値として扱う既存の簡略化に
合わせて合算表示する。`/tax-estimate`への自動反映は機能53で対応した(ロードマップ参照)。

### 53. 住民税の調整控除の`/tax-estimate`統合(税額控除としての自動反映) — `src/lib/residentTaxAdjustmentDeduction.ts`・`src/lib/taxEstimate.ts`

機能52で「住宅ローン控除・外国税額控除と同様、引き続き今後の課題」としていた
`/tax-estimate`の合計税額試算への自動反映に対応した。ロードマップで課題として
挙げていた「控除適用の順序(住宅ローン控除・外国税額控除・調整控除のどれを
先に所得割額から差し引くか)」は、静岡市・石井町等の複数の自治体公式サイトで
確認できる住民税の税額控除の適用順序(調整控除→配当控除→住宅借入金等特別
税額控除→寄附金税額控除→外国税額控除)に基づき、調整控除→住宅ローン控除→
外国税額控除の順で整理した(配当控除・寄附金税額控除は本アプリで税額控除として
モデル化していないため対象外)。

`ResidentTaxAdjustmentDeductionRecord`テーブルを追加し、`/resident-tax-adjustment-deduction`
の「この試算結果を◯年分の住民税の調整控除として登録する」ボタンから登録できるように
した(住宅ローン控除・外国税額控除と同じ登録パターン)。調整控除は住民税所得割のみに
適用され所得税には対応する控除が無い制度のため、住民税分の控除額1列のみを保持する。
`/tax-estimate`は住宅ローン控除を適用する**前**の住民税額から調整控除を差し引き、
その適用後の住民税額を基準に住宅ローン控除・外国税額控除の限度判定を行う(控除額が
残りの住民税額を上回る場合は0円が下限)。

ふるさと納税の上限額試算(`furusatoNozei.ts`)の基準となる住民税所得割額も、
実際の速算式が「調整控除後の所得割額」を基準とすることに合わせ、調整控除適用後
(住宅ローン控除等それ以外の税額控除適用前)の住民税額を渡すよう変更した。これにより
機能51時点では未考慮だった調整控除による上限額の目減りが試算結果に反映されるように
なった(住宅ローン控除・外国税額控除・均等割は従来通り基準額に含めない)。

### 54. 一般株式等(非上場株式)の譲渡所得等の分離計算 — `src/lib/investment/`・`src/lib/taxEstimate.ts`・`src/lib/etax/`

これまで機能2の株式等の譲渡損益計算は、上場株式等・非上場株式(一般株式等)の
区別なく単一のプールとして合算していた。国税庁の実務上、両者は別プールの
申告分離課税(税率はいずれも20.315%で同じ)として扱われ、両者の間で損益通算は
できない。さらに、譲渡損失の繰越控除(措置法37の12の2・3年間)は上場株式等のみに
認められた制度で、一般株式等の譲渡損失には繰越控除が無く当年限りで切り捨てられる。
`InvestmentTrade`(`OpeningBalance`を含む)に`isListed`区分(既定値true。この機能
追加前の登録済みデータはすべて上場株式等として扱われ、挙動は変わらない)を追加し、
`/import`の株式等取引フォーム・期首残高フォームでチェックを外すと一般株式等
(非上場株式)として登録できるようにした。

計算エンジン(`src/lib/investment/calculator.ts`)自体は変更せず、`src/lib/reporting.ts`
の`buildYearReport`で`isListed`により取引・期首残高を振り分けたうえで
`calculateInvestmentPortfolioYear`を2回(上場株式等分・一般株式等分)呼び出す
方式にした。一般株式等分は繰越控除制度が無いため、`nonListedInvestmentTaxableGainJpy`
として当年の譲渡損益をそのまま課税対象額とし、赤字の場合のみ0円に切り捨てる
(翌年以後への繰越は行わない)。`/tax-estimate`の合計税額試算にも、上場株式等・
先物取引と並ぶ独立した申告分離課税プールとして追加した(`estimateTotalTax`の
`nonListedInvestmentTaxableGainJpy`引数。省略時は0円で従来の呼び出しと互換)。
下書きCSV(`/api/export`)・ダッシュボードにも、一般株式等分の譲渡所得等・
銘柄別内訳を上場株式等分とは別区分で出力・表示するようにした。

NISA口座は上場株式等・ETF・株式投資信託等のみが対象の制度のため、
`isNisa=true`かつ`isListed=false`の組み合わせは登録時に拒否する。一般株式等
(非上場株式)の配当等はCSV上で参考値として集計するのみで、上場株式等のような
総合課税・申告分離課税・申告不要の選択制のシミュレーション(機能6)には含めない
(非上場株式の配当は原則総合課税のみで申告分離課税を選べない制度上の違いがあり、
既存の`dividendTaxSimulation.ts`をそのまま適用すると誤った試算になるため)。
一般株式等の配当所得自体の税額試算への対応は引き続き今後の課題とする。

### 55. 一般株式等(非上場株式)の配当所得の税額試算 — `src/lib/investment/dividendTaxSimulation.ts`・`/dividend-simulation`

機能54で「総合課税のみが原則で上場株式等のような課税方式の選択制が無い」ことを
理由に今後の課題としていた、一般株式等(非上場株式)の配当所得の税額試算に対応した。

上場株式等の配当と異なり申告分離課税は選択できず、総合課税(配当控除あり)が
原則だが、1回に受け取る配当金額が「10万円×配当計算期間の月数÷12」以下の
少額配当(措置法8条の5)に該当する部分のみ、所得税(復興特別所得税を含む)に
限り確定申告不要制度を選択できる(源泉徴収税率20.42%で確定し、配当控除は
使えない)。上場株式等の配当と異なり、所得税で申告不要を選んでも住民税は
免除されず、少額配当であっても常に他の所得と合算した総合課税での申告が必要に
なる点(地方税法の規定。中央区・柏市等の自治体公式サイトで確認)を踏まえ、
住民税額は所得税側の選択にかかわらず常に配当所得全額を総合課税で計算する
(`src/lib/investment/dividendTaxSimulation.ts`の`simulateNonListedDividendTaxation`)。

少額配当の判定は配当の支払い1回ごとに行う必要があるが、本ツールは取引明細を
支払い単位までは区別していないため、該当額はユーザー自身の判定に基づく入力
とする簡略化とした。また、一般株式等の配当は普通株式の配当(配当控除率が
通常税率)のみを想定し、非上場の投資信託等、配当控除が半分税率・対象外となる
銘柄種別の区別には対応していない(今後の課題)。`/dividend-simulation`の初期値
には、機能54で追加された`investmentNonListed`(一般株式等の年間集計)の配当
受取額をそのまま使えたため、DBスキーマの変更は不要だった。

### 56. 配当所得の課税方式シミュレーションにJ-REIT型ETFの配当控除対象外区分を追加 — `src/lib/investment/calculator.ts`・`prisma/schema.prisma`・`/import`

機能45で「ETFのうちJ-REIT型(本来は配当控除の対象外)を区別する銘柄種別の
細分化は引き続き対象外」としていた簡略化に対応した。J-REIT(不動産投資法人が
発行する投資証券)は、利益の90%超を分配する等の要件を満たすことで法人税が
実質非課税になる仕組みのため、株式の配当と異なり法人段階・個人段階の二重課税が
生じず、配当控除の対象外となる(国税庁タックスアンサーNo.1330「配当所得が
あるとき(配当控除)」で、配当控除の対象となる配当等から「特定投資法人(いわゆる
J-REIT)から受ける配当等」が除外されている旨を確認)。取引所に上場している点は
通常のETFと同じで銘柄コードからは区別できないため、`InvestmentTrade`に
`isReit`区分(既定値false。機能追加前の登録済みデータはすべて通常のETF等として
扱われ挙動は変わらない)を追加した。

`assetType`による配当控除率区分の判定(`src/lib/investment/calculator.ts`の
`dividendCreditCategory`)を、`assetType="ETF"`かつ`isReit=true`の場合のみ
対象外(NONE)に振り分けるよう変更した(`assetType`がETF以外の場合、`isReit`の
値にかかわらず従来通りの区分のまま)。`/import`の株式・投資信託等取引フォームに
「J-REIT(不動産投資信託)」チェックボックス(資産種別がETFの場合のみ指定する
想定。それ以外を選んだままチェックすると登録時にエラーとする)を追加し、
登録済み取引一覧にも資産種別と合わせて表示するようにした。`/dividend-simulation`側は
機能45で既に`dividendCreditCategory`の集計結果(`totalDividendNoCreditJpy`等)を
そのまま使う設計だったため変更不要だった。

### 57. 配当所得の課税方式シミュレーションに株式投資信託の1/4税率(組入割合50%超)区分を追加 — `src/lib/investment/calculator.ts`・`src/lib/investment/dividendTaxSimulation.ts`・`prisma/schema.prisma`・`/import`・`/dividend-simulation`

機能45で「株式投資信託の半分税率は外貨建資産等の組入割合が50%以下であることを
前提とする簡略化で、組入割合50%超75%以下の場合はさらに率が下がる(1/4)」と
していた点に対応した。国税庁タックスアンサーNo.1250「配当所得があるとき
(配当控除)」の速算表で、証券投資信託の収益の分配に係る配当控除率が組入割合
50%以下(通常の1/2)・50%超75%以下(通常の1/4)・75%超(対象外)の3段階に
分かれていることを確認したうえで実装した。

`InvestmentTrade`に`mutualFundHighForeignRatio`区分(既定値false。機能追加前の
登録済みデータはすべて組入割合50%以下として扱われ挙動は変わらない)を追加し、
`dividendCreditCategory`(`src/lib/investment/calculator.ts`)が
`assetType="MUTUAL_FUND"`かつ`mutualFundHighForeignRatio=true`の場合のみ
新設の`QUARTER`区分(国税2.5%/1.25%・住民税0.7%/0.35%、通常税率の1/4)に
振り分けるよう変更した。組入割合75%超は本来対象外(NONE)になるが、この区分
までは細分化しておらず75%超もQUARTERとして扱う簡略化とした(対象外より
有利になる方向の簡略化のため実害は小さいと判断。今後の課題)。

`src/lib/investment/dividendTaxSimulation.ts`の`DividendCreditBreakdown`に
`quarterCreditJpy`を追加し、1,000万円の配当控除枠の消費順序を「通常税率→
半分税率→1/4税率」の3段階に拡張した。`/import`の株式・投資信託等取引フォームに
「外貨建資産等の組入割合が50%超75%以下」チェックボックス(資産種別が投資信託の
場合のみ指定する想定。それ以外を選んだままチェックすると登録時にエラーとする)を
追加し、`/dividend-simulation`の内訳入力欄にも1/4税率の欄を追加した。

## データモデル

`prisma/schema.prisma` を参照。主なテーブル:

- `TaxYear` — 課税年度(暦年)単位でデータを区切る
- `CryptoTrade` — 暗号資産(現物)の取引明細
- `CryptoMarginTrade` — 暗号資産の証拠金(レバレッジ)取引の決済損益明細
- `InvestmentTrade` — 株式・投資信託等の取引明細(口座区分・NISA区分・
  NISA枠区分(nisaType)・国外源泉フラグ(isForeign)・
  外国所得税額(foreignTaxWithheldJpy)・上場株式等/一般株式等区分(isListed。
  既定値true。機能54参照)・J-REIT型ETF区分(isReit。既定値false。機能56参照)を保持)
- `FuturesTrade` — FX・先物・CFD等(先物取引に係る雑所得等)の決済損益明細。
  上場株式等の譲渡所得・暗号資産の雑所得とは別プールで計算する
- `OpeningBalance` — 各課税年度の期首残高(前年繰越分の保有数量・取得価額)。
  投資分はNISA区分(isNisa)・上場株式等/一般株式等区分(isListed。機能54参照)
  ごとに別レコード
- `OpeningBalanceByInstitution` — 期首残高の金融機関別内訳(任意)。
  `OpeningBalance`とは独立した追加データで、マネーフォワード資産残高突合の
  数量チェックで複数金融機関にまたがる銘柄の按分に使う
- `InvestmentLossCarryforward` — 上場株式等の譲渡損失の繰越控除残高
  (発生年ごとの、各課税年度初時点での未使用残高)
- `FuturesLossCarryforward` — 先物取引に係る雑所得等(FX・先物・CFD等)の
  損失の繰越控除残高(発生年ごとの、各課税年度初時点での未使用残高。
  InvestmentLossCarryforwardとは別プール)
- `BrokerAnnualReport` — 証券会社の特定口座年間取引報告書との突合用の
  年間サマリー数値(証券会社・口座区分ごとの収入金額・取得費・配当等の額)
- `AssetBalanceSnapshot` — マネーフォワードの資産残高突合用の、金融機関・
  資産別の残高スナップショット
- `AssetSymbolMapping` — マネーフォワードの資産名とアプリの銘柄シンボルの
  対応表(年に依存しない共通マスタデータ)。資産残高突合の銘柄単位判定に使う
- `MarketPrice` — 銘柄ごとの現在価格(時価)の手入力(年に依存しない共通
  マスタデータ)。資産残高突合の評価額比較と`/unrealized-gain`の初期値に使う
- `ForeignTaxCreditCarryforward` — 外国税額控除の繰越控除限度超過額
  (発生年ごとの、各課税年度初時点での未使用残高)
- `ForeignTaxCreditSpareLimitCarryforward` — 外国税額控除の繰越控除余裕額
  (発生年ごとの、各課税年度初時点での未使用残高。限度超過額側と対になる繰越)
- `CasualtyLossCarryforward` — 雑損失の繰越控除残高(発生年ごとの、各課税年度初
  時点での未使用残高。雑損控除額が総所得金額等を超えて控除しきれなかった超過額)
- `IncomeDeduction` — 所得控除試算画面(医療費控除・生命保険料控除・
  地震保険料控除・小規模企業共済等掛金控除・社会保険料控除・
  セルフメディケーション税制・配偶者控除/配偶者特別控除・扶養控除・基礎控除・

  登録した年分・控除区分ごとの
  控除額(所得税用・住民税用)。`/tax-estimate`の初期値算出に使う。医療費控除と
  セルフメディケーション税制は選択制のため合計額算出時は有利な方のみを反映する
  (`src/lib/incomeDeduction.ts`参照)
- `MortgageDeductionRecord` — 住宅ローン控除(税額控除)の年分ごとの試算結果
  (所得税分・住民税分の控除額)。`/mortgage-deduction`から登録し、
  `/tax-estimate`の合計税額試算へ自動反映するために使う
- `ForeignTaxCreditRecord` — 外国税額控除(税額控除)の年分ごとの試算結果
  (合計控除額、および所得税・復興特別所得税から控除される額/住民税から
  控除される額の内訳)。`/foreign-tax-credit`から登録し、下書きCSVの税額控除欄
  (合計控除額)・`/tax-estimate`の合計税額試算(所得税分・住民税分の内訳)へ
  自動反映するために使う
- `ResidentTaxAdjustmentDeductionRecord` — 住民税の調整控除(税額控除)の
  年分ごとの試算結果(控除額)。調整控除は住民税所得割のみに適用され所得税に
  対応する控除が無いため住民税分の1列のみ保持する。
  `/resident-tax-adjustment-deduction`から登録し、`/tax-estimate`の合計税額試算
  (住宅ローン控除・外国税額控除より先に住民税額から控除)へ自動反映するために使う
- `NisaLifetimeQuota` — NISA生涯投資枠(総枠1,800万円)の使用状況試算用に、
  各課税年度の年始時点で確定している非課税枠使用額(前年末の保有簿価残高)を
  枠区分(つみたて投資枠/成長投資枠)ごとに保持する。当年中に売却した保有分の
  取得価額(簿価)も手入力で保持し、翌年への繰越額(=翌年の年始使用額)の
  算出に使う
- `ImportBatch` / `CashflowEntry` — マネーフォワード等からの取り込みバッチと明細

## ロードマップ(次回以降のブラッシュアップ候補)

優先度が高いと思われる順:

1. **暗号資産取引所CSVの実データ検証・対応拡大** — bitFlyer・Coincheck・
   GMOコイン・bitbankの実エクスポートCSVで列見出し・値の揺れを検証し、
   一致しないものは`src/lib/crypto/exchangeCsv.ts`のプリセットやエイリアスに
   反映する(特にbitbankは公開情報から推定した仕様のため実データでの検証が
   未了)。証拠金取引の決済損益CSV(`src/lib/crypto/marginCsv.ts`)も同様に、
   DMM Bitcoin/SBI VCトレード等の実データに基づくプリセット化は今後の課題。
   なお、手動マッピング欄自体の入力補助として、よく使われる列名(日本語・英語)
   からの自動認識(`parseCryptoExchangeCsv`によるプリセット「その他」の
   フォールバック)と、自動認識に失敗した場合の列見出し・売買値の候補一覧
   (`<datalist>`)表示は対応済み(完了済み参照)。証拠金取引の決済損益CSVも
   自動認識こそ行わないが、手動マッピング欄への列見出し候補一覧表示は
   対応済み(機能36参照)。自動認識できないCSVの実データを集めてエイリアス
   (`HEADER_ALIASES`)や証拠金取引の候補(`COMMON_MARGIN_CSV_HEADER_NAMES`)を
   拡充していくのが次の課題。
2. **証券会社の特定口座年間取引報告書のPDF自動取り込み(実PDFでの検証)** —
   CSV一括取り込み(`src/lib/investment/annualReportCsv.ts`)に加え、PDFから
   コピーしたテキストのラベルベース読み取り(`src/lib/investment/
   annualReportText.ts`。機能37参照)にも対応したが、あくまで構成した
   サンプルテキストでの検証にとどまり、実際の証券会社発行PDFから抽出した
   テキストでの検証はできていない。証券会社によって「譲渡の対価の額」等の
   ラベルと金額の位置関係(同一行か、離れた列か)が異なる可能性があるため、
   実データでの検証・ラベルパターンの拡充が今後の課題。また、画像化された
   (テキスト層のない)PDFへの対応(OCR)は引き続き対象外。
3. **住宅ローン控除の令和10年(2028年)以降の「災害レッドゾーン」判定** —
   機能44で令和8年(2026年)〜令和12年(2030年)入居分の借入限度額・控除期間に
   対応したが、令和10年(2028年)以降入居の新築住宅が土砂災害特別警戒区域等の
   「災害レッドゾーン」に所在するかどうかの判定は行っていない(ユーザー自身の
   確認事項として注記表示のみ)。都道府県が公開するハザードマップ等との突合は
   住所情報を扱う必要があり本ツールのスコープを超えるため、引き続き対象外の
   まま注記での対応にとどめるのが妥当かは次回以降の検討課題。

上記3件はいずれも実データや住所情報の突合が前提で自動化セッションでは検証・実装が
難しいため、次回以降のブラッシュアップでは、README中に散在する他の「今後の課題」
(例: 一般株式等(非上場株式)の配当所得の税額試算(機能55)が普通株式の配当
(配当控除率が通常税率)のみを想定しており、非上場の投資信託等、配当控除が
半分税率・1/4税率・対象外となる銘柄種別の区別に対応していない点等、実データ依存が
少なく一次情報の確認と既存パターンの踏襲で対応しやすい項目)の中から実現可能なものを
選んで対応するのが妥当と考えられる。

- **配当所得の課税方式シミュレーションに株式投資信託の1/4税率(組入割合50%超)区分を追加**

  今後の課題としていた、一般株式等(非上場株式)の配当所得の税額試算に対応した。
  上場株式等と異なり申告分離課税は選択できず、総合課税(配当控除あり)が原則だが、
  1回に受け取る配当金額が「10万円×配当計算期間の月数÷12」以下の少額配当
  (措置法8条の5)に該当する部分のみ、所得税(復興特別所得税を含む)に限り
  確定申告不要制度を選択できる(源泉徴収税率20.42%で確定し、配当控除は
  使えない)。上場株式等の配当と異なり、所得税で申告不要を選んでも住民税は
  免除されず、少額配当であっても常に他の所得と合算した総合課税での申告が

  本ツールは取引明細を支払い単位までは区別していないため、該当額はユーザー
  自身の判定に基づく入力とする簡略化とした。また、一般株式等の配当は普通株式

  (`AssetSymbolMapping`テーブル・`src/lib/moneyforward/assetBalanceReconciliation.ts`の
  `reconcileAssetSymbolBalances`・`/import`の「銘柄マッピング」セクション)。
  マネーフォワードの資産名とアプリの銘柄シンボルの対応表をユーザーが登録
  できるようにし、従来の金融機関単位の突合に加えて「金融機関×銘柄」単位で
  取引明細の有無を判定できるようにした。数量・評価額そのものの比較は
  時価の扱いが自動化できないため引き続き対象外(ロードマップ参照)。
- **証券会社の特定口座年間取引報告書のCSV一括取り込み**
  (`src/lib/investment/annualReportCsv.ts`・`/import`の専用フォーム)。
  証券会社・口座区分ごとの年間サマリー数値(譲渡の対価の額・取得費・配当等の額)
  を1行にまとめたCSVを、他の取引所CSVと同様の列名指定による汎用マッピング
  方式で一括登録できる。口座区分の日本語表記ゆれもある程度吸収する。
  様式が確認できているPDF自動解析は未対応(引き続きロードマップ参照)。
- **マネーフォワード資産残高との突合(取引漏れ検出)**
  (`AssetBalanceSnapshot`テーブル・`src/lib/moneyforward/parseAssetBalance.ts`・
  `src/lib/moneyforward/assetBalanceReconciliation.ts`・`/import`の専用
  セクション)。マネーフォワードの「資産の内訳」CSVを取り込み、残高がある
  金融機関のうちアプリに取引明細が無いものを検知する。銘柄単位の数量突合は
  今後の課題(ロードマップ参照)。
- **証券会社の特定口座年間取引報告書との突合(手入力)**
  (`BrokerAnnualReport`テーブル・`src/lib/investment/annualReportReconciliation.ts`・
  `/import`の専用セクション)。証券会社が発行する年間取引報告書の
  「譲渡の対価の額(収入金額)」「配当等の額」を証券会社・口座区分ごとに
  入力すると、アプリ内の取引明細から計算した同条件の合計値と自動で突き合わせ、
  差額があれば一覧に表示する。取得費は口座ごとの管理と本ツールの計算前提が
  異なるため自動突合の対象外とし、参考表示に留めた。CSV/PDFからの自動取り込み
  は未対応(今後の課題、ロードマップ参照)。
- **暗号資産の証拠金(レバレッジ)取引の決済損益への対応**
  (`CryptoMarginTrade`テーブル・`src/lib/crypto/marginCalculator.ts`・
  `src/lib/crypto/marginCsv.ts`・`/import`の専用セクション)。DMM Bitcoin/SBI
  VCトレード等の証拠金取引は決済時の建玉損益がそのまま雑所得になるため、
  現物取引とは別のシンプルな合算モデルとして実装し、ダッシュボード・下書き
  CSVでは現物取引分と合算した雑所得(暗号資産)を表示する。
- **bitbankの約定履歴CSV取り込み**(`src/lib/crypto/exchangeCsv.ts`)。
  現物取引の行のみを対象にし、信用取引の行はスキップする。
- **暗号資産取引所CSV取り込みの重複実装を整理** — 過去のブラッシュアップで
  マージが重なり、実際にはUIから使われていない重複パーサー

- **前年繰越残高のUI対応**(`OpeningBalance`テーブル・`/import`の期首残高セクション・

## 免責事項

本ツールは税額計算を補助するための個人開発ツールであり、税務署・国税庁の
公式ツールではない。計算結果の正確性を保証するものではなく、実際の申告内容は
必ず国税庁「確定申告書等作成コーナー」の計算結果や、税理士等の専門家の確認を
受けること。
